# 📌 ESP32-S3 기반 얼굴 인식 출입 시스템 아키텍처

# **시스템 목표**

- ESP32-S3 단말기에서 **얼굴 검출 → 임베딩 생성 → 사용자 비교 → 출입 여부 판단**을 모두 처리
- 태블릿(Web UI)을 통해 **관리자 모드** (**등록 / 삭제 / 사용자 목록 / 실시간 카메라 확인 / 출입 로그 확인)** 기능 제공
- 서버는 출입 로그를 저장하는 역할만 수행

---

# **전체 구성요소**

## 1) **ESP32-S3 얼굴 인식 단말기**

- OV2640 사용 (esp-who 가 ov5640 지원 안함)
- 실시간 얼굴 인식 Loop 수행
- 인식 결과를 서버로 POST
- Web UI를 위한 HTTP 서버 동작 (스트림 + 등록 API + 삭제 API 등 제공)
- 사용자 얼굴 임베딩 DB는 보드 내부 SPI Flash(FATFS) `/spiflash/faces.bin` 파일로 영구 저장

## 2) **태블릿(Web UI, 브라우저 기반)**

보드 IP에 접속하여 Web UI 사용

예) `http://192.168.xx.xx/`

노출되는 화면 구성:

| 항목 | 기능 |
| --- | --- |
| 📸 카메라 화면 | 사람 위치 맞추기 |
| 👤 등록 | 이름 입력 + 샘플 캡처 5장 |
| 🗑 삭제 | 등록된 사용자 리스트 + 삭제 버튼 |
| 👤 사용자 목록 | 등록된 사용자 리스트  |
| 📄 로그 조회 | 서버 DB 조회 |

### **1. 실시간 카메라 화면**

- 현재 들어오는 사람 얼굴 확인 가능
- 관리자 사용 목적 - 인식이 잘 되는지 확인하는 용도

### **2. 사용자 등록 기능**

- 사용자 이름 입력
- ESP32가 1–3장의 얼굴을 자동 촬영하여 임베딩(512차원 벡터) 생성
- 생성된 임베딩 + 이름 정보를 **보드 내부 Flash DB (`faces.bin`)에 저장**
    
    예:
    
    ```jsx
    # faces.bin 내부
    
    face_count
    ├─ face[0]
    │   ├─ name: "홍길동"
    │   ├─ embedding_dim: 512
    │   └─ embedding[512] (float32)
    ├─ face[1]
    │   ├─ name: "이몽룡"
    │   ├─ embedding_dim: 512
    │   └─ embedding[512]
    └─ ...
    ```
    

### **3. 사용자 삭제 기능**

- 현재 등록된 사용자 리스트 표시
- 각 사용자 옆에 “삭제” 버튼
- 삭제 시 ESP32가 **해당 사용자의 레코드를 DB(메모리)에서 제거 후, `faces.bin`을 다시 저장**

### **4. 사용자 목록**

- 현재 **보드 내부 Flash DB(`faces.bin`)**에 저장된 모든 사용자 정보를 기반으로 리스트 표시
- ESP32가 `faces.bin`을 읽어서 아래와 같은 JSON 형태로 응답한다고 가정:
    
    ```jsx
    [
    	{
    		"id": 1,
    		"name": "홍길동",
    		"num_embeddings": 1
    	},
    	{
    		"id": 2,
    		"name": "이몽룡",
    		"num_embeddings": 1
    	}
    ]
    ```
    

### **5. 출입 로그**

- 출입 인증이 일어날 때마다 ESP32가 서버 API로 로그 전송
- 태블릿 Web UI는 서버 DB에서 로그를 가져와 표로 표시
    
    예:
    
    | 시간 | 사용자 | confidence |
    | --- | --- | --- |
    | 2025-11-25 10:14 | 홍길동 | 0.87 |
    | 2025-11-25 10:16 | Unknown | — |

## 3) **서버(DB 저장용 API)**

- 단말기가 인식한 결과를 저장하는 역할만 수행
- Web UI의 “출입 로그” 화면에서 사용할 데이터를 제공
- API 예:
    - `POST /api/log { userId(or name), timestamp, confidence, result }`
    - `GET /api/logs` → UI에서 로그 조회

8. 출입 결과를 서버로 전송 (`POST /api/logs`)
9. threshold 미만 → “unknown” 처리

## 3. 스트리밍 HTTP 서버 구성

### 3-1. 엔드포인트

- `/` : 간단한 HTML 페이지
    - `<img src="/stream">`로 MJPEG 스트림을 그대로 띄움
- `/stream` : `multipart/x-mixed-replace; boundary=frame` 형식의 MJPEG 스트림

### 3-2. 스트림 처리 방식

- 루프 내에서:
    - `fb = s_cam->cam_fb_get()` 로 프레임 받아옴
    - 프레임이 **JPEG**인 경우:
        - 헤더(`-frame`, `Content-Type: image/jpeg`, `Content-Length`) 전송
        - `fb->buf`를 그대로 HTTP chunk로 전송
    - 프레임이 **JPEG가 아닌 경우**:
        - 로그:
            
            `W (...) FACE_V0_1: Stream: non-JPEG frame (format=2)`
            
        - 해당 프레임은 스트림에서 사용하지 않고 버림
- 현재 로그상 상태:
    - `format=2` → 내부 enum 상으로 **RGB565 포맷**으로 추정
    - 즉, **카메라가 JPEG 모드가 아니라 RGB565 모드**로 동작 중
    - 그래서 **브라우저에 실제 영상이 안 나오는 상태**

## 4. 얼굴 검출·인식 파이프라인 구성 시도

### 4-1. 사용한 라이브러리/모델

- 헤더
    - `#include "human_face_detect.hpp"`
    - `#include "human_face_recognition.hpp"`
- 실제 구현체
    - `HumanFaceDetect` (wrapper)
        - 내부에 `MSR` + `MNP` 조합(MSRMNP)을 쓰는 구조
    - `HumanFaceRecognizer`
        - 얼굴 임베딩 모델 (`HumanFaceFeat`) 사용
        - 내부적으로 DB(`dl::recognition::DataBase`)를 이용해 등록된 임베딩과 비교

### 4-2. face_recog_task 흐름

- FreeRTOS Task `face_recog_task` 생성
    - 우선 Wi-Fi/HTTP 서버와 **병렬로 동작**
- 내부 루프 동작
    1. `cam_fb_t* fb = s_cam->cam_fb_get();`
    2. 프레임 포맷 확인
        - 원래는 RGB565 기반으로 바로 `dl::image::img_t` 생성하려고 했음
        - 스트리밍을 위해 JPEG도 유지해야 해서,
            
            → 현재는 **JPEG 프레임을 RGB888로 변환하는 방향**으로 변경 시도
            
    3. `dl::image::img_t img` 생성
        - `data = 변환된 RGB 버퍼`
        - `width = fb->width`
        - `height = fb->height`
        - `pix_type = DL_IMAGE_PIX_TYPE_RGB888` (또는 RGB565 시도)
    4. 얼굴 검출
        - `auto dets = detector.run(img);`
        - 검출 결과 없으면:
            - 로그: `I (...) FACE_V0_1: No face`
    5. 얼굴 인식 / similarity 계산
        - `auto res = recognizer.recognize(img, dets);`
        - 결과가 있으면:
            - `Face detected, similarity=0.xxx` 식으로 로그 출력 예정
        - 결과 없으면:
            - `Face detected but no match` 로그

## 5. 실제 관측된 동작 & 문제점

### 5-1. 스트리밍 쪽

- 모니터 로그:
    - `W (...) FACE_V0_1: Stream: non-JPEG frame (format=2)`
- 의미
    - 카메라 프레임 포맷이 JPEG가 아니라 RGB565로 들어오고 있음
    - `/stream` 핸들러는 JPEG만 전송하도록 짰기 때문에,
        - 실제 브라우저에서는 **영상이 나오지 않거나, 계속 끊김/에러 가능성** 높음

### 5-2. 얼굴 검출/인식 쪽

- 로그 패턴:
    - 대부분 `No face`
    - 간헐적으로:
        - `Face detected, num_boxes=1`
        - 그 뒤에
            
            `dl::recognition::DataBase: Failed to open db.`
            
            `Face detected but no match (DB size=15409)`
            
- 여기서 추정되는 상황
    - **검출 모델(detector)은 어느 정도 동작**하고 있음
        - 얼굴 있을 때 `num_boxes=1` 등 로그가 찍힘
    - **인식 모델(recognizer) 쪽 DB 경로/구성이 애매함**
        - `/tmp` 같은 경로로 DB를 열려고 하다가 실패 로그
        - 하지만 `DB size=15409` 같은 수치가 나오는 걸 보면,
            - 내부적으로 기본 DB/버퍼가 초기화돼 있거나,
            - 메모리 상의 초기 값이 예상과 다르게 읽히는 상황일 가능성
    - 아직 **명확한 “similarity=0.xx” 형태의 정상 출력까지는 못 감**

### 5-3. 타입/포맷 관련 기술적 문제

- `who::cam::cam_fb_fmt_t` vs `pixformat_t`
    - `WhoS3Cam`이 반환하는 포맷 타입과
        
        `fmt2rgb888()` / ESP32-CAMERA가 기대하는 `pixformat_t`가 달라서
        
    - 캐스팅/변환 과정에서 컴파일 에러 및 경고 발생
- `PIXFORMAT_JPEG` vs `RGB565` 충돌
    - 스트리밍은 JPEG 필요
    - FD/인식은 RGB 기반 필요
    - 현재는
        - 카메라를 RGB565로 세팅했다가 → 스트림이 깨짐
        - JPEG로 세팅하면 → FD 입력용 RGB 변환이 필요 (fmt2rgb888)

## 6. 지금까지의 정리된 결론

1. **ESP-WHO 최신 버전 + ESP-IDF v5.4.2 조합**으로 가는 방향은 맞다.
2. `WhoS3Cam` 기반으로
    - Wi-Fi 연결
    - HTTP MJPEG 스트림 엔드포인트(`/`, `/stream`) 구축
    - 얼굴 검출/인식 Task(`face_recog_task`) 병렬 구동
        
        까지는 코드 구조를 잡아놓은 상태
        
3. 하지만,
    - **카메라 포맷(JPEG vs RGB565)**
    - **스트림용 JPEG와 인식용 RGB 변환**
    - **인식 DB(파일 경로, 최초 상태)**
        
        이 세 군데에서 꼬이면서
        
    - 스트림이 제대로 안 보이고
    - 얼굴 검출/인식도 “No face / no match” 로그만 나오는 상태.
4. 근본적으로는
    - goouuu S3-CAM + OV2640에 맞춰
    - `esp_camera_init()`으로 직접 `camera_config_t`를 구성해서
    - **“JPEG로 캡처 → 스트림에는 그대로 사용, FD에는 RGB로 변환해서 사용”**
        
        구조로 가는 게 가장 안정적이라고 판단된 상황
