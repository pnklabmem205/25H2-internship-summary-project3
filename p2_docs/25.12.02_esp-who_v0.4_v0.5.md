## 1. 목표

- v0.4.1 기능 + **플래시 내부 FATFS 파티션(storage)에 DB 저장**
- 부팅 시:
    - `/spiflash/faces.bin`을 읽어서 `s_face_db` 복원
    - 등록된 사람이 있으면 곧바로 인식 가능
- **플래시 내부 FATFS 파티션(storage)에 DB 저장이 무엇인가**
    - ESP32-S3 플래시는 다음과 같은 여러 ‘칸’으로 나뉘어 있음:
    
    ```jsx
    [ 부트로더 | 파티션 테이블 | 펌웨어(factory) | NVS | ... | storage 파티션 ]
    ```
    
    - storage 파티션이 사용할 ‘작은 하드디스크’ 같은 구역
        - 이 storage 위에 FATFS 파일 시스템을 올려서 `“/spiflash”` 라는 경로로 마운트 해서 사용
            - 마운트: 어떤 저장공간을 컴퓨터가 ‘폴더처럼’ 사용할 수 있도록 연결하는 과정
                - 예) USB를 PC에 연결하여 드라이브로  쓰게 하는 과정
        - `“/spiflash/faces.bin”` ⇒ storage 파티션 안에 있는 FATFS 디스크에 faces.bin 이라는 파일을 만들어라
            - FATFS (파일 시스템): 파일을 어떻게 저장하고 찾을지 정해놓은 규칙
    - faces.bin 파일 안에는 다음과 같은 내용과 순서가 들어가게됨:
        - (1) 헤더 (파일 정보)
            - 이 파일이 진짜 내 얼굴DB 맞는지 + 몇 명 들어있는지 + 벡터가 몇 차원인지 등을 알려줌
            
            ```jsx
            [ MAGIC (4바이트) ]
            [ VERSION (4바이트: 혹은 2+2) ]
            [ FACE_COUNT (4바이트) ]
            [ EMBEDDING_DIM (4바이트) ]
            ```
            
            예를 들어:
            
            - MAGIC: `'F''D''B''1'` → 0x46 0x44 0x42 0x31
                - “이 파일은 내가 만든 Face DataBase 1버전이다” 이런 마크
            - VERSION: 1
            - FACE_COUNT: 지금 저장된 사람 수 (예: 3명)
            - EMBEDDING_DIM: 임베딩 벡터 차원 수 (512)
        - (2) 사람 별 데이터
            - 사람 1명당 대략 이런 구조:
            
            ```jsx
            [ NAME_LEN (4바이트) ]
            [ NAME (NAME_LEN 바이트 만큼) ]
            [ EMBEDDING (float 512개 = 4 * 512바이트) ]
            ```
            
            예를 들어 `name = "person1"`이고 dim=512라면:
            
            1. `NAME_LEN = 7`
            2. `"person1"` 이라는 글자 7바이트 그대로 저장 (`'p' 'e' 'r' 's' 'o' 'n' '1'`)
            3. `embedding[0]`, `embedding[1]`, ..., `embedding[511]`
                
                → 각각 `float` 형태(4바이트)로 이진(binary)로 저장
                
            - 사람이 3명이면:
            
            ```
            [헤더]
            [사람1] (name_len, name, embedding 512개)
            [사람2] (name_len, name, embedding 512개)
            [사람3] (name_len, name, embedding 512개)
            ```
            
    - faces.bin은 PC 디스크에 있는 파일이 아니라 ESP32-S3 보드 안 플래시(storage 파티션)에 있는 파일이기 때문에 직접 열어 확인할 수는 없음 (보드 내부 파일 경로)

## 2. 새로 관여하는/중요해진 파일들

### 2-1) `components/who_peripherals/who_spiflash_fatfs.*`

- esp-who에서 제공하는 **FATFS 마운트용 유틸**

```cpp
esp_err_t fatfs_flash_mount()
{
    esp_vfs_fat_mount_config_t mount_config;
    memset(&mount_config, 0, sizeof(esp_vfs_fat_mount_config_t));
    mount_config.max_files = 5;
    mount_config.format_if_mount_failed = true;

    ESP_ERROR_CHECK(esp_vfs_fat_spiflash_mount_rw_wl(
        CONFIG_SPIFLASH_MOUNT_POINT,
        CONFIG_SPIFLASH_MOUNT_PARTITION,
        &mount_config,
        &wl_handle));
    return ESP_OK;
}
```

- `CONFIG_SPIFLASH_MOUNT_POINT="/spiflash"`
- `CONFIG_SPIFLASH_MOUNT_PARTITION="storage"`

→ 즉, **플래시 파티션 “storage”를 `/spiflash`라는 경로에 FATFS로 마운트**하는 코드

### 2-3) `main/face_processor.cpp`

### (1) 파일 포맷 & 헬퍼 함수 추가

- RAM에만 있던 `s_face_db`를 **Flash에 저장/로드**하기 위해 다음이 추가됨:
1. **파일 경로 상수**

```cpp
static const char *FACE_DB_FILE = "/spiflash/faces.bin";
```

1. **바이너리 포맷 구조체 정의**

```cpp
struct FaceDbHeader {
    uint32_t magic;      // 0xFACEB00C 같은 값
    uint16_t version;    // 포맷 버전
    uint16_t reserved;
    uint32_t face_count; // 등록된 얼굴 수
};

struct FaceEntryHeader {
    uint16_t name_len;   // 이름 길이
    uint16_t dim;        // embedding 차원(예: 512)
};
```

1. **저장 함수**

```cpp
static bool save_face_db_to_flash();
```

- 역할:
    - `fopen(FACE_DB_FILE, "wb")`
    - `FaceDbHeader` → 각 얼굴별 `FaceEntryHeader + name + embedding` 순으로 쓰기
    - 성공하면 로그:
        - `save_face_db: saved X faces to /spiflash/faces.bin`
1. **로드 함수**

```cpp
static bool load_face_db_from_flash();
```

- 역할:
    - `fopen(FACE_DB_FILE, "rb")`
    - 헤더 검사(magic, version, face_count)
    - 루프 돌면서 name + 벡터를 읽어 `s_face_db` 복원
    - 성공하면:
        - `load_face_db: loaded X faces from /spiflash/faces.bin`
1. **한 번만 로드하는 플래그**

```cpp
static bool s_db_loaded = false;
```

- `process_and_draw()`에서 **처음 호출될 때**:

```cpp
    if (!s_db_loaded) {
        load_face_db_from_flash();
        s_db_loaded = true;
    }
```

→ 부팅 직후 첫 프레임 처리 시에만 플래시에서 DB를 읽어오고, 그 다음부터는 계속 RAM에 있는 `s_face_db` 사용

## 사용자 삭제 (/face_delete)

- ‘삭제’ 버튼 → ESP32에 `/face_delete` 요청 → 메모리에서 사람 정보 지움 → 바뀐 내용 다시 flash에 저장(faces.bin)
    1. **이름으로 삭제**: ‘삭제’ 탭에서 ‘이름’ 검색 후 삭제 요청
        - `/face_delete?name=이름`
    2. **ID로 삭제**: ‘등록된 사용자 리스트’ 탭에서 각 행 오른쪽 ‘삭제’ 버튼 누르면 ‘id=0’ 식의 번호로 삭제 요청
        - `/face_delete?id=번호`

### 얼굴 정보가 저장되는 구조

- **RAM(메모리) 안에 있는 목록**
    - 보드가 켜지면, 등록된 사람들을 벡터(배열 같은 것)에 들고 있음
    - 각 사람은
        - 이름(예: `"person1"`)
        - 얼굴 임베딩(숫자 벡터)  이런 정보를 가지고 있음
- **Flash 안에 있는 파일 (`faces.bin`)**
    - 전원을 꺼도 안 날아가게 **SPI Flash에 `faces.bin` 파일로 한 번 더 저장**해둠
    - 실행할 때 한 번 이 파일을 읽어서 → 메모리(RAM)로 가져옴
        
        (그래서 삭제/등록이 모두 이 메모리 목록을 기준으로 동작함)

### 브라우저(HTML/JS) 쪽 로직

### 1) 이름으로 삭제할 때

1. 사용자가 **삭제 탭**에서 이름을 입력하고, “이름으로 삭제” 버튼 클릭
2. JS가:
    - `http://<ESP_IP>/face_delete?name=<입력한이름>`이런 식으로 요청 보냄
3. 서버 응답이:
    - 성공이면 → “삭제 완료”
    - 실패면 → “삭제 실패(이름 없음 등)”
        
        이런 식으로 상태 영역에 표시
        

### 2) ID로 삭제할 때

1. 사용자가 **리스트 탭**에서 “삭제” 버튼 클릭
2. JS가 내부에서 이런 식으로 동작함:
    - 현재 설정된 ESP IP를 기준으로
        
        → `http://<ESP_IP>/face_delete?id=<해당ID>`이런 GET 요청 보냄
        
3. 서버에서 성공 응답이 오면
    - “삭제 완료” 같은 텍스트를 오른쪽 상태창에 보여주고
    - **다시 목록을 새로 불러와서** 테이블 갱신함

### ESP32 서버 쪽 로직 (http_server_ex)

서버는 `/face_delete` 요청을 받았을때의 동작:

1. URL에 뭐가 들어왔는지 확인
    - `id`가 있는지?
    - `name`이 있는지?
    - 둘 다 없으면 → 잘못된 요청으로 처리 (400 에러)
2. 경우 나누기
    - `id`가 있으면 → “ID로 삭제하는 함수” 호출
    - `name`이 있으면 → “이름으로 삭제하는 함수” 호출
3. 삭제 성공 여부에 따라 응답
    - 삭제 성공 → 200 OK + `"deleted"` 텍스트
    - 삭제 실패(없는 ID/이름, 저장 실패 등) → 404 + `"delete failed (not found?)"`

### FaceProcessor 내부 삭제 로직

- 실제 리스트에서 지우는 작업은 `FaceProcessor` 안에서 함

### 1) 공통: DB 로드 보장

- 어떤 삭제 함수든 먼저:
    - **한 번만 `faces.bin`을 읽어서** RAM 안에 `s_face_db`(얼굴 목록)를 채워둠
    - 이미 읽었다면 또 안 읽고 재사용

### 2) 이름으로 삭제 로직

1. 등록된 사람들을 앞에서부터 쭉 보면서
    - `name`이 같은 사람을 찾음
2. 첫 번째로 이름이 같은 사람을 발견하면
    - 그 사람을 배열에서 제거
    - 다시 `faces.bin`에 저장
3. 끝까지 돌았는데 못 찾으면
    - “그런 이름 없음” → 실패

### 3) ID로 삭제 로직

1. “등록된 사람 배열”에서 `index`번째 사람을 가리킴
2. 만약 **index가 범위를 벗어나면**
    - “그런 사람 없음” → 실패 반환
3. 범위 안이면
    - 그 사람을 배열에서 제거
    - 수정된 배열을 **다시 `faces.bin`에 저장**
    - 저장도 성공하면 → 삭제 성공

## 사용자 목록 (/faces)

### 동작 개요

- 오른쪽 패널에서 **‘리스트’ 탭 클릭**
- JS에서 **스트리밍 중지 → ESP32에 `/faces` 요청**
- ESP32는 **RAM에 올라와 있는 얼굴 목록을 JSON으로 응답**
- 브라우저는 이 JSON을 파싱해서 **ID · 이름 · 삭제 버튼**이 있는 테이블로 렌더링

### 브라우저(HTML/JS) 쪽 로직

1. 사용자가 **‘리스트’ 탭 클릭**
    - 탭 전환 이벤트에서:
        - `stopStream()` 호출
            
            → `<img id="streamImg">.src = ''` 로 설정해 스트림 연결 끊기
            
        - `fetchFaceList()` 호출
            
            → `GET /faces` 요청 전송
            
2. `fetchFaceList()` 동작
    1. 상태 표시
        - 상단 상태 영역에
            
            `listStatus.textContent = '조회 중...'`
            
    2. `/faces` 요청 및 응답 파싱
        - `fetch('/faces')` → 응답 본문을 `text()`로 받음
        - `JSON.parse()`로 파싱해서 `data` 객체 생성
        - JSON 형식 예:
        
        ```json
        {
          "count": 2,
          "faces": [
            { "id": 0, "name": "yh" },
            { "id": 1, "name": "abc" }
          ]
        }
        ```
        
        ![image.png](attachment:a6c1683e-dbe0-4883-a103-53c5666ad24d:image.png)
        
        - `data.faces`를 배열로 꺼냄
        - 상단 상태 영역에 `등록 인원: 2` 표시
    3. 테이블 렌더링
        - `<tbody>`를 한 번 싹 비움
            
            → `faceTableBody.innerHTML = ''`
            
        - `faces` 배열을 돌면서 각 항목에 대해 `<tr>` 생성:
            - 1열: ID (`face.id`)
            - 2열: 이름 (`face.name`)
            - 3열: 삭제 버튼
        - 각 행의 삭제 버튼에는 `deleteFaceById(face.id)`를 호출하도록 클릭 핸들러 연결
3. 리스트에서 **삭제 버튼 클릭 시 동작**
    - `confirm('ID N 을(를) 삭제할까요?')`로 사용자 확인
    - 확인 시:
        - `stopStream()` 호출 → 스트림 중지
        - `fetch('/face_delete?id=N')` 요청
        - 응답이 성공이면:
            - 상태 영역에 `"삭제 완료\n..."` 표시
            - `fetchFaceList()` 다시 호출 → 갱신된 목록으로 테이블 다시 그림
        - 실패 시:
            - `"삭제 실패(...)"` 문구 표시

### FaceProcessor 내부 목록 관리

1. **RAM 상의 얼굴 DB 구조**
    - FaceProcessor는 실행 중 동안 **RAM에 얼굴 DB를 유지**하고 있음
        
        (실제 타입은 구현에 따라 다르지만 개념적으로는 아래와 유사)
        
    
    ```cpp
    struct FaceEntry {
      std::string name;
      std::array<float, 512> embedding;
    };
    std::vector<FaceEntry> s_face_db;
    ```
    
2. **시작 시 로드**
    - 프로그램 시작 시:
        - `/spiflash/faces.bin` 파일이 존재하면:
            - 이진 파일을 읽어서 `s_face_db` 벡터에 채움
        - 파일이 없으면:
            - “등록된 사람 없음” 상태에서 시작
3. **/faces 요청 시 동작**
    - `/faces`가 들어오면:
        - 이미 메모리에 올라와 있는 `s_face_db`를 그대로 사용
        - `count = s_face_db.size()`
        - `faces[i].id = i`,
            
            `faces[i].name = s_face_db[i].name`
            
            형태로 JSON을 구성
            
4. **등록/삭제와의 관계**
    - `/register`(등록) 또는 `/face_delete`(삭제)가 성공하면:
        1. `s_face_db`를 수정 (추가 / 제거)
        2. 수정된 전체 내용을 **다시 `faces.bin`으로 덮어쓰기 저장**
    - 따라서:
        - `/register` / `/face_delete`는
            
            → **DB 갱신 + Flash 재저장**
            
        - `/faces`는
            
            → **현재 RAM DB 상태를 그대로 JSON으로 뿌리는 read-only API**
