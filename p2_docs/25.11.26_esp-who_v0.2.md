    ## 1. 현재 스트림 경로에서 벌어지는 일
    
    ```cpp
    cam_fb_t *fb = s_cam->cam_fb_get();
    ...
    if ((pixformat_t)fb->format != PIXFORMAT_JPEG) {
        ESP_LOGW(TAG, "Stream: non-JPEG frame (format=%d)", (int)fb->format);
    }
    
    char hdr[64];
    int hdr_len = snprintf(hdr, sizeof(hdr),
                           "--frame\r\n"
                           "Content-Type: image/jpeg\r\n"
                           "Content-Length: %u\r\n\r\n",
                           fb->len);
    
    httpd_resp_send_chunk(req, hdr, hdr_len);
    httpd_resp_send_chunk(req, (char *)fb->buf, fb->len);
    httpd_resp_send_chunk(req, "\r\n", 2);
    
    ```
    
    - HTTP 응답 헤더에는 **무조건**
        
        `Content-Type: image/jpeg` 로 보내고 있음.
        
    - 그런데 로그를 보면:
        
        ```
        W (...) FACE_V0_1: Stream: non-JPEG frame (format=2)
        
        ```
        
        이 말은:
        
        - `fb->format` 값이 `PIXFORMAT_JPEG`이 아니고 `2`라는 뜻이고,
        - 이 값은 보통 **RGB565 같은 비압축 포맷**에 해당함.
    - **근데 우리 스트리밍 코드**는 이렇게 생각하고 있음:
        
        > “카메라는 JPEG을 주겠지?”
        > 
        > 
        > → 그래서 `fb->buf`를 **그냥 JPEG라고 믿고 브라우저로 보내는 중**
        > 
    - 브라우저 입장:
        
        > “어, 받은 데이터가 JPEG 규칙이 아닌데?”
        > 
        > 
        > → 그래서 **화면에 그림을 못 그리는 거고, 그냥 까만 화면**이 되는 것.
        > 
    
    그래서:
    
    - 서버 코드 자체는 돌아가고,
    - 로그도 잘 찍히는데,
    - **브라우저 화면은 안 나오는 상태**가 되는 거.
    
    ---
    
    ## 2. “그럼 분명히 JPEG로 설정했는데 왜 format=2가 찍히냐?”
    
    여기서 살짝 의심해야 하는 부분이 이 줄:
    
    ```cpp
    s_cam = new WhoS3Cam(PIXFORMAT_JPEG, FRAMESIZE_QVGA, 5, false, true);
    ```
    
    우리는 이렇게 써놨지:
    
    - “야, JPEG 모드로 만들어줘”라고 **WhoS3Cam 생성자에 요구**한 거고,
    
    근데 실제로 **드라이버가 어떻게 반응하는지**는:
    
    - `WhoS3Cam` 내부에서 `esp_camera_init()`에 어떤 config 넣는지
    - 그 안에서 OV2640이 JPEG을 지원 안 한다고 판단하면 RGB로 fallback 하는지
    - 또는 sdkconfig 쪽 다른 옵션 때문에 강제로 RGB로 도는지
    
    이걸 까 보지 않으면 **“인자=JPEG”라고 줬다고 진짜 JPEG로 돈다고 확신할 수 없음**.
    
    앞에서 찍힌 로그:
    
    ```
    W (...) FACE_V0_1: Stream: non-JPEG frame (format=2)
    ```
    
    이게 사실상 **증거**야.
    
    - `fb->format`이 2 = 내부 enum으로 RGB565처럼 보이고,
    - 즉, WhoS3Cam이 실제로는 **RGB565 프레임을 계속 올려 보내고 있음**.
    
    우리는 그걸 모르고 “JPEG라고 가정하고 그냥 던지는” 상태.
    
    ---
    
    ## 3. 얼굴 검출/인식 코드랑의 관계
    
    지금 `face_recog_task`에서는 이렇게 하고 있지:
    
    ```cpp
    bool ok = fmt2rgb888(
        (const uint8_t *)fb->buf,
        fb->len,
        (pixformat_t)fb->format,
        s_rgb_buf
    );
    ```
    
    - 이쪽은 **fb->format을 캐스팅해서 제대로 넘기고 있음.**
    
    즉:
    
    - 카메라가 RGB565이면 → `fmt2rgb888(RGB565 → RGB888)` 이건 합리적인 경로.
    - 카메라가 JPEG이면 → `fmt2rgb888(JPEG → RGB888)` 이것도 지원되는 패스.
    
    그래서 **FD 쪽은** “어느 정도는” 정상적으로 놔둘 수 있어.
    
    문제는:
    
    - **스트리밍 경로는 변환을 안 함**
    - 포맷 확인만 하고 **경고만 찍은 뒤에도 그냥 JPEG라고 속여서 송신**
    
    결론적으로:
    
    > 얼굴 검출 코드랑 충돌해서 스트림이 깨지는 게 아니라,
    > 
    > 
    > **애초에 스트림 쪽이 “JPEG라고 믿고 RGB를 내보내는” 구조라서** 깨지는 거다.
    > 
    
    ---
    
    ## 4. 그래서, 왜 “스트리밍이 안 되는지” 요약
    
    1. `WhoS3Cam`이 실제로는 **JPEG가 아닌 포맷(format=2)** 로 프레임을 주고 있음.
    2. `stream_handler()`는
        - **Content-Type: image/jpeg**로 고정,
        - 변환 없이 `fb->buf` 그대로 내보냄.
    3. 브라우저는 “JPEG”라고 받아서 디코딩해 보다가
        - JPEG 시그니처가 아니니 **이미지를 못 그림**.
    4. 코드/로그는 정상처럼 보이지만,
        - **화면에는 아무것도 안 나옴.**
    
    ---
    
    ## 5. 앞으로 어떻게 가야 하는지(방향만 짚어두면)
    
    지금 단계에서 선택지는 딱 셋이야:
    
    1. **정말 JPEG로 카메라를 돌리게 만들기**
        - WhoS3Cam 내부 config를 확인하거나,
        - 아예 `esp_camera_init()` 직접 써서
            
            `config.pixel_format = PIXFORMAT_JPEG`로 강제.
            
        - 그러면 `/stream`은 지금 코드 그대로 써도 됨.
    2. **RGB565 그대로 쓰되, 스트림 전송 전에 JPEG로 변환**
        - `frame2jpg()` 같은 걸 이용해서:
            - `RGB565 → JPEG 버퍼`로 인코딩
            - 그걸 `/stream`으로 쏨.
        - 대신 CPU 부하 + 딜레이 증가 감수.
    3. **이 둘을 섞어서 구조 재정리**
        - 스트림용 카메라는 JPEG,
        - FD/인식용은 `/stream`에서 쓰는 프레임을 그대로 받아다가
            
            `fmt2rgb888(JPEG → RGB888)`로 변환해서 사용.
            
    
    지금 코드에서 스트리밍이 안 나오는 이유는 “얼굴 FD 붙여서 꼬였다”가 아니라:
    
    > 카메라 출력 포맷과 스트림 코드의 전제가 서로 안 맞아서임.
    > 
- 이를 해결하기 위한 두 가지 방법
    - A. `WhoS3Cam` 포맷을 확실히 JPEG로 만드는 쪽(= esp_camera로 직접 설정)
        
        ## 1. 방식 A – 카메라를 **처음부터 JPEG 모드**로 돌리는 경우
        
        ### 구조
        
        - 카메라: `PIXFORMAT_JPEG`
        - 스트리밍: `fb->buf` 그대로 HTTP로 전송 (지금 너가 이미 하고 있는 방식)
        - 얼굴 검출: `fmt2rgb888(JPEG → RGB888)` 후 `HumanFaceDetect.run(img)`
        1. **카메라 설정**
            
            ```cpp
            new WhoS3Cam(PIXFORMAT_JPEG, FRAMESIZE_QVGA, ...);
            
            ```
            
            → “사진을 **JPG 파일 형태**로 바로 찍어줘”라고 카메라에 부탁하는 거야.
            
        2. **스트리밍**
            - 카메라가 준 `fb->buf`는 **그 자체가 JPG**라서
            - 우리는 그냥:
                
                ```cpp
                httpd_resp_send_chunk(req, fb->buf, fb->len);
                
                ```
                
            - 이렇게만 해도 브라우저가
                
                > “아, 이건 JPG네” 하고 바로 보여줄 수 있어.
                > 
        3. **얼굴 검출 / 인식**
            - 근데 딥러닝 모델은 **JPG 그대로 못 쓰고, 풀어야 함**.
            - 그래서:
                
                ```cpp
                fmt2rgb888(JPEG → RGB888)
                
                ```
                
            - 즉,
                
                > “압축된 JPG를 다시 풀어서,
                > 
                > 
                > 딥러닝이 먹을 수 있는 일반 RGB 사진으로 변환”
                > 
            - 변환된 RGB 데이터를 `HumanFaceDetect.run(img)`에 넘김.
        
        ### 장점
        
        - **스트리밍은 상대적으 쉽다**
            - 카메라 → 바로 브라우저.
                
                딱히 중간에 변환 안 해도 됨.
                
        - **문제 발생 시 원인 추적이 쉽다**
            - 스트림 안 나오면:
                - Wi-Fi, HTTP, 브라우저 쪽 보면 됨.
            - FD 안 되면:
                - `fmt2rgb888` / 모델 / 임계값 쪽 보면 됨.
            - 영상 포맷이 한 번만 바뀌니까 머리가 덜 아프다.
        - **문 앞 카메라 용도에는 충분히 빠름**
            - 사람이 1초 안에 인식되면 OK인데,
            - JPG → RGB 변환이 조금 무겁긴 해도
                
                **Qvga+0.5~1초 주기 정도는 충분히 커버 가능**.
                
        
        ### 단점
        
        - **CPU가 하는 일이 늘어난다**
            - 매번 JPG → RGB 변환이 필요한데,
                
                이게 “그냥 포맷 바꾸기”가 아니라 **압축 풀기(디코딩)**라 좀 무거운 작업이야.
                
        - **메모리도 더 쓴다**
            - 압축된 JPG 버퍼 + 풀린 RGB 버퍼
                
                두 개가 동시에 필요.
                
    - B.  `frame2jpg()`를 써서 RGB → JPEG 변환하는 쪽
        
        ## 2. 방식 B – 카메라를 **RGB565로 돌리고, 스트리밍 전용으로만 JPEG 인코딩(frame2jpg)**
        
        ### 구조
        
        - 카메라: `PIXFORMAT_RGB565`
        - 얼굴 검출: `fmt2rgb888(RGB565 → RGB888)` or RGB565 직접 처리
        - 스트리밍: `frame2jpg(RGB565 → JPEG)` 한 뒤 HTTP로 전송
        
        ### 어떻게 동작하냐?
        
        1. **카메라 설정**
            
            ```cpp
            new WhoS3Cam(PIXFORMAT_RGB565, ...);
            
            ```
            
            → 카메라가 **압축 안 된 색 정보(RGB565)**를 그대로 줌.
            
        2. **얼굴 검출 / 인식**
            - 이건 오히려 더 자연스러워:
                - 딥러닝 입장에서 원래 RGB 계열 입력을 기대하니까.
            - `fmt2rgb888(RGB565 → RGB888)` 정도만 해주면 됨.
            - 압축 풀기(JPG 디코딩)가 아니라, **그냥 색 포맷만 바꾸는 정도**라서 디코딩보단 부담이 덜함.
        3. **스트리밍**
            - 문제는 여기서 나옴.
            - 브라우저는 여전히 **JPG를 원함.**
            - 그런데 우리는 RGB565 생사진을 갖고 있으니까:
                - 매 프레임마다:
                    
                    ```cpp
                    frame2jpg(RGB565 → JPEG)
                    
                    ```
                    
                - 이렇게 직접 JPG를 만들어서 HTTP로 던져야 함.
        
        ### 장점
        
        - **AI(인식) 입장에서는 더 “깔끔한 사진”**
            - 압축 아티팩트 없는, 원본에 가까운 색 정보라서
                
                이론적으로 인식이 더 안정적일 수 있음.
                
        - **FD/인식만 놓고 보면 구조가 심플**
            - 카메라 → RGB → FD/인식 끝.
        
        ### 단점
        
        - **스트리밍이 진짜 무거워짐**
            - 매 프레임마다 **JPG 인코딩**을 해야 하는데,
            - 인코딩은 디코딩보다도 더 비싸고,
            - 거기에 FD까지 같이 돌리면:
                - 스트림 끊김
                - FPS 확 떨어짐
                - 인식 주기를 줄여야 함
                - 이런 일이 쉽게 벌어진다.
        - **코드 복잡도 + 디버깅 난이도 상승**
            - “왜 안 보이지?” 했을 때
                - 카메라 문제인지,
                - JPG 인코딩 문제인지,
                - 메모리 문제인지,
                - FD 때문인지…
            - 확인해야 할 지점이 많아진다.
    - GPT 추천
        
        ## 4. 그래서, 현실적인 추천
        
        너 프로젝트 목표를 다시 보면:
        
        - **보드 단독 얼굴 인식 → 서버에는 “누가 언제 출입했는지”만 기록**
        - PC/브라우저는 **“제대로 작동하는지 확인하는 모니터용 도구”**
        - 상시로 30fps 풀 스트림을 예쁘게 보여주는 CCTV가 아니라,
            
            **디버깅 + 간단한 모니터링 용도**
            
        
        이 조건에서 보면 나는 이렇게 판단해:
        
        > 🔵 방식 A – 카메라 JPEG 모드가 더 낫다.
        > 
        
        ### 그 이유를 요약하면
        
        1. **스트리밍 쪽이 매우 단순하고 안정적**
            - 카메라 → 바로 MJPEG 스트림,
                
                esp-who / esp32-camera에서 검증된 패턴이라 삽질 포인트가 적음.
                
        2. **FD/인식의 주기를 너 마음대로 줄일 수 있음**
            - 모든 프레임에 FD 안 돌리고:
                - 500ms마다 1프레임만 FD,
                - 사람이 감지될 때만 FD 등
            - 이렇게만 해도 CPU/메모리 부담이 훨씬 줄어듦.
        3. **유지보수/확장 관점에서 esp-who 최신 구조와 잘 맞음**
            - 나중에 SD 카드 DB, 등록/삭제, REST API, WebUI 붙일 때도
                - “스트림 == JPEG”
                - “AI == JPEG → RGB888”
            - 라는 단순한 분리가 유지됨.
        4. **문제 생겼을 때 원인 추적이 덜 꼬임**
            - 스트림 깨지면 → “카메라 JPEG 설정 or Wi-Fi or 브라우저” 범위.
            - 인식 실패하면 → “JPEG 디코딩, FD 모델, 임계값, DB” 범위.
            - RGB565 + frame2jpg 조합보다 디버깅 범위가 더 좁음.
        
        ---
        
        ## 5. 정리
        
        - **방식 A (카메라 JPEG)**
            - 스트리밍: 매우 안정적·단순
            - FD/인식: JPEG→RGB888 디코딩 부담 있지만, 주기 조절로 충분히 제어 가능
            - esp-who 최신 구조/문서와 더 잘 맞음 → 앞으로 기능 확장에도 유리
        - **방식 B (RGB565 + frame2jpg)**
            - 이론상 FD 성능에는 조금 더 좋은 입력이 될 수 있지만,
            - 실용적인 문 앞 카메라 용도 + 스트리밍까지 고려하면
                
                **CPU/메모리/복잡도 리스크가 더 큼**
                
        
        그래서 지금 이 프로젝트 전체 로드맵(등록/삭제, SD DB, 서버 로그 전송까지)을 생각하면,
        
        > 카메라는 JPEG 모드 유지
        > 
        > - FD/인식용에서만 `fmt2rgb888` 써서 RGB888 만들고
        > - FD 주기를 적당히(예: 0.5~1초) 제한하는 방향

## ESP32-S3 얼굴 검출 + 스트리밍 문제 해결 정리

## 1. 문제 상황

### ❗ 발생했던 문제들

- 스트리밍 **안됨**
- 얼굴 검출은 가끔 되고 갑자기 **WDT 에러 → 보드 리부팅**
- `No face` 계속 출력
- `fmt2rgb888 failed`, `Stream: non-JPEG frame` 같은 경고 발생
- 두 작업(스트리밍/FD)이 **안정적으로 동시에 동작하지 않음**

---

## 2. 원인 (아주 쉽게 설명)

### ❌ 원인 1: **카메라 프레임을 두 군데에서 동시에 가져감**

- 스트리밍 코드 → `fb = s_cam->cam_fb_get()`
- 얼굴검출 코드 → 또 `fb = s_cam->cam_fb_get()`

→ **카메라가 하나인데 두 명이 동시에 뺏어감**

→ 프레임 충돌, 타이밍 꼬임, 포맷 꼬임, WDT 발생

---

### ❌ 원인 2: **fb->format을 그대로 믿고 fmt2rgb888 에 넣음**

- 센서가 JPEG로 주는지 RGB565로 주는지 보드마다 다름
- 실제 포맷과 FD에서 사용하는 포맷이 일치하지 않아서
    
    `fmt2rgb888` 변환 실패 → No face 반복
    

---

### ❌ 원인 3: HumanFaceDetect 모델의 기본 score_thr(약 0.5)이 높음

- QVGA 해상도 + 조명 + 렌즈 상태 때문에
- 자신 있는 얼굴만 인식하려다 보니 대부분 No face 로 필터됨

---

## 3. 최종 해결 방향

### 해결 1: **카메라는 한 곳에서만 읽는다 (단일 캡처 태스크)**

→ `capture_and_detect_task` **한 태스크만 카메라 프레임을 가져감**

나머지는:

- 스트리밍 → 공유 JPEG 버퍼만 읽음 (카메라 안 건드림)
- 얼굴검출 → 캡처 태스크가 RGB888로 변환해서 처리

---

### 해결 2: **JPEG 포맷 고정**

카메라를 확실히 JPEG 모드로 설정:

```cpp
s_cam = new WhoS3Cam(PIXFORMAT_JPEG, FRAMESIZE_QVGA, 5, false, true);
```

그리고 FD 변환도 **무조건 JPEG로 인식**:

```cpp
fmt2rgb888(fb->buf, fb->len, PIXFORMAT_JPEG, s_rgb_buf);
```

→ 포맷 헷갈림 0%

---

### 해결 3: **0.5초마다 얼굴검출 (부하 줄이기)**

캡처 태스크에서:

```cpp
const TickType_t detect_interval = pdMS_TO_TICKS(500);
```

→ 스트리밍은 30fps

→ 얼굴 검출은 2fps

→ 서로 부하 격리됨

---

### 해결 4: **score threshold 낮추기 (0.35 정도)**

```cpp
HumanFaceDetect detector(0.35f);
```

→ 얼굴을 더 관대하게 감지

→ 실제로 바로 인식됨

---

## 4. 현재 구조

### 🔥 동작 흐름 요약

```
[카메라]
    ↓ (단일 태스크)
capture_and_detect_task()
    ├── 최신 JPEG → s_stream_buf에 저장 (스트리밍용)
    └── 0.5초마다:
            JPEG → RGB888 변환
            HumanFaceDetect 실행
```

### 🌐 스트리밍 (/stream)

- s_stream_buf 를 HTTP로 전송
- 카메라에 절대 접근 안함
    
    → PC가 켜져 있든 꺼져 있든 **보드 내부 FD는 계속 동작**

httpd_resp_send_chunk(req, (char*)s_stream_buf, s_stream_len);

}

cam_fb_t* fb = s_cam->cam_fb_get();
