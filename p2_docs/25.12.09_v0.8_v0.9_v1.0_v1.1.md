# v1.0 임베딩 구조 변경

- 변경 파일(코드): `human_face_recognition\main\face_processor.cpp`

https://github.com/pnkmem432/esp-who-face_entry/blob/v1.0/examples/human_face_recognition/main/face_processor.cpp

### 1. 현재 임베딩 구조

### 지금 코드의 핵심 패턴

```cpp
// 같은 이름 있으면 "평균 임베딩"으로 누적
for (auto &f : s_face_db) {
    if (f.name == name) {
        if (f.embedding.size() == embedding.size()) {
            for (size_t i = 0; i < embedding.size(); ++i) {
                f.embedding[i] = (f.embedding[i] + embedding[i]) * 0.5f;
            }
        } else {
            f.embedding = embedding;
        }
        replaced = true;
        break;
    }
}
if (!replaced) {
    // 새 사람 추가
}
```

- **이름 기준으로 1명당 임베딩 1개**만 유지
- 다시 찍으면 **기존 + 신규 / 2 로 평균**
- `faces.bin`에도 결국 사람당 **벡터 1개**만 저장

그래서:

- 사람당 N장 등록하고, 각각을 따로 들고 있다가 인식할 때 N개 중 제일 높은 값 쓰기를 하려면
    
    → 지금 패턴(평균으로 덮어쓰기)은 반드시 바꿔야 함
    
- 반대로,
    - 사람당 N장을 찍되, 결국 하나의 평균 벡터만 쓸 거야면
        
        → 지금 패턴을 약간 다듬는 정도로 이어갈 수 있음
        

---

### 2. 같은 이름으로 여러 번 등록을 했을 때 임베딩 구조는 2 case로 구현 가능

1. 평균 내서 덮어쓰기
2. 각각 저장하고 인증할 때 가장 높은 임베딩 모델 사용 → 정확도는 더 올라갈 수 있음
    - esp-who HumanFaceDetect 모델은 **정면~약간 측면(살짝 고개 돌린 정도)** 기준으로 학습된 모델이라 왼쪽, 오른쪽 (고개 90도 돌렸을 때) 모습만 보고는 얼굴 검출이 안됨
    - 사용자 별로 N 장을 등록할 수 있지만 그래봤자 비슷한 사진이 등록되어 오히려 메모리만 쌓일 순 있음

---

### 3. 변경 임베딩 구조

### 목표

- 사람 = 이름 1개 + 샘플 N개
- 샘플 = 임베딩 벡터 1개
- 같은 이름으로 여러 번 등록하면
    
    → 그 사람 아래에 샘플이 계속 쌓이고
    
    →**인식할 때는 그 샘플들 중 최댓값(sim)을 사용**
    
- 샘플 개수 정책:
    - 사람당 최대 5개 `MAX_SAMPLES_PER_PERSON = 5`
    - 새로 추가할 때:
        - 5개 미만 → push_back
        - 5개 이상 → 제일 오래된 것 삭제 후 push_back (FIFO)

### 3.1 메모리 상 구조

코드 상으로 변경된 구조체

- **RegisteredFaceSample**
    - `embedding`: `std::vector<float>`
        
        → 이 샘플의 임베딩 벡터 (512차원)
        
- **RegisteredFace**
    - `name`: `std::string`
        
        → 사람 이름
        
    - `samples`: `std::vector<RegisteredFaceSample>`
        
        → 이 사람의 모든 샘플 목록
        
- **전체 DB**
    - `std::vector<RegisteredFace> s_face_db;`
    - 즉,
        - `s_face_db[0]` = 사람 A (`name="user1"`, 샘플 여러 개)
        - `s_face_db[1]` = 사람 B (`name="user2"`, 샘플 여러 개)
        - ...

**핵심 차이점**

- 예전: `RegisteredFace` 안에 `embedding` 딱 1개
- 지금: `RegisteredFace` 안에 `samples` 벡터가 있고, 그 안에 `embedding`이 여러 개

### 3.2 faces.bin 파일 포맷 변경

- 파일 헤더는 그대로 사용하되, 버전만 v1 → v2 로 올림:
    - `magic`: `0xFACEB00C`
    - `version`: `2`
    - `count`: 등록된 사람 수
- **v2에서 사람 한 명이 저장되는 형태**
    1. `name_len` (uint32)
    2. `name` (바이트 배열, 길이 = name_len)
    3. `sample_count` (uint32)
    4. 샘플들 반복 (`sample_count` 번):
        - `dim` (uint32)
        - `embedding` (float[dim])

> 헤더 → (이름 길이 + 이름 + 샘플 개수 + [샘플 dim + 샘플 임베딩] × 샘플 개수) × 사람 수
> 

### 3.3 등록 로직 변화

1. **현재 프레임에서 임베딩 추출**
    - `extract_embedding_from_frame(fb, out_embedding)`
    - 얼굴 1개 검출 → keypoints → 임베딩 벡터(`dim=512`) 뽑아냄
2. **이 임베딩을 DB에 저장**
    - `register_face_with_embedding(embedding, name)` 호출
    - 내부 동작:
        1. `s_face_db`에서 같은 이름의 사람 찾기
        2. 없으면:
            - `RegisteredFace person; person.name = name;`
            - `s_face_db.push_back(person);`
        3. 있으면:
            - `person.samples` 길이 확인
            - `MAX_SAMPLES_PER_PERSON` 초과하면 **맨 앞 샘플 삭제(FIFO)**
            - 새 `RegisteredFaceSample`을 만들어 `embedding` 넣고 `push_back`
        4. `save_face_db()`로 faces.bin 저장
- 같은 이름으로 5번 등록하면
    - 메모리: 그 사람 `samples.size() == 5`
    - 파일: 동일하게 샘플 5개가 저장
- 6번째부터는
    - 가장 오래된 샘플이 하나씩 밀려나고 최근 샘플 기준으로 5개만 유지

### 3.4 인증 로직 변화

1. 현재 프레임에서 검출된 얼굴 박스를 하나 잡고
2. 이 박스 기준으로 임베딩 `cur`를 뽑는다
3. 그 다음 **전체 사람 + 그 사람의 모든 샘플**에 대해 유사도를 돈다
- 이전: 사람당 “대표 임베딩 1개”와만 비교
- 지금: 사람당 “N개 샘플 중 최댓값”을 사용
    - 즉, 다양한 환경·거리·표정에서 찍은 샘플이 쌓이면 그 중 하나는 지금 프레임과 잘 맞을 가능성이 올라가고, 그 최댓값을 쓰기 때문에 **threshold 근처에서 살짝 더 유리한 구조**가 됨
    - 물론 샘플만 늘리면 무조건 성능이 올라간다 는 보장은 전혀 없고 너무 비슷한 사진만 여러 장 쌓으면 의미가 없음
    - 실제로는:
        - 조명/거리/각도 조금씩 다르게 찍어 주는 게 의미 있음
        - MAX_SAMPLES_PER_PERSON도 너무 크게 잡기보다 3~5 선에서 조정하는 게 현실적

## 1. 보드 쪽 구현 흐름

### 1.1 얼굴 등록/삭제가 일어났을 때

**(1) 얼굴 등록 버튼 누름 → 보드 흐름**

1. 카메라에서 얼굴 1장을 찍음
2. 얼굴 특징(임베딩)을 계산
3. DB에 추가
4. DB 전체를 다시 faces.bin 파일로 저장

**결과:** 등록할 때마다 DB 전체를 다시 저장하므로 데이터 무결성이 유지됨

**(2) 얼굴 삭제 버튼 누름 → 보드 흐름**

1. 보드 내부 DB에서 해당 사람 삭제
2. 다시 faces.bin 파일을 새 상태로 저장

**결과:** 삭제 후에도 서버에 최신 faces.bin 백업을 남겨둘 수 있음

### 1.2 ‘서버에서 얼굴 DB 가져오기’ 버튼 클릭 시 보드 흐름

1. 웹 UI → `/faces_restore` 로 요청 전송
2. 보드가 서버로 요청: `GET /api/faces-db/LAB`
3. 서버가 저장해둔 faces.bin 다운로드
4. 보드는 파일을 `/spiflash/faces.bin`으로 교체
5. DB를 다시 메모리에 로드
6. 즉시 인식에 반영됨

**결과:** 보드의 얼굴 정보가 서버 백업을 기준으로 완전히 복구됨

### 1.3 DB가 없을 때의 동작

- `/spiflash/faces.bin`이 없으면 → 빈 DB로 시작
- 얼굴은 검출되지만 **아무도 등록자로 인식되지 않음**
- ‘서버에서 얼굴 DB 가져오기’ 버튼을 누르면 `복구 실패(500): download failed` 로 뜨게

## 2. 서버 동작 흐름

### 2.1 저장 구조

```jsx
faces_storage/
	LAB/
		faces.bin
	SHOP001/
		faces.bin
```

- device_id 별 폴더가 나뉘어 저장됨 → 여러 보드를 운영할 때를 고려

### 2.2 서버 API 기능

- **업로드 (보드 → 서버)**

`POST /api/faces-db/{device_id}`

→ 보드가 faces.bin을 보내면 서버가 해당 파일을 그대로 저장

- **다운로드 (서버 → 보드)**

`GET /api/faces-db/{device_id}`

→ 저장된 faces.bin 을 그대로 반환

→ 없으면 404 반환
